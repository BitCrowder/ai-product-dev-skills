# PRD 生成器使用说明

## 这个 Skill 解决什么问题

它把产品想法、研究结论或会议纪要整理成一份能被设计、工程、测试和数据共同使用的 PRD，并把范围、事实边界和未决决策显式保留下来。

## 为什么普通提示词容易失败

直接说“写 PRD”常会得到流畅但不可执行的清单：把想法当问题、把纪要当事实、把所有人提到的内容塞进 MVP，只写成功路径，或给出没有事件定义的指标。该 Skill 强制先分离证据、假设和决策，再定义可测试的范围。

## 适合谁使用

产品经理、创始人、设计负责人、工程负责人和跨职能项目负责人，尤其适合在立项、范围评审、试用准备或将研究结论交接给实现团队时使用。

## 使用前准备什么

尽量提供以下最小输入包；不知道就写 `[待确认]`，不要用猜测替代：

```text
要支持的决策、决策人和截止时间：
产品/业务目标与不可触碰限制：
目标用户、情境、JTBD、当前替代方案：
研究、数据、反馈、纪要或既有决策及其来源/日期：
候选范围、已知非目标、平台、容量、依赖与合规限制：
成功信号、现有指标/埋点、基线与发布约束：
```

## 推荐调用方式

先说明你要用 PRD 支持的决定，例如“决定是否以现有客户试用某流程”，再贴原始材料。明确要求保留证据标签、MVP/后续候选/非目标、状态覆盖、埋点、验收、依赖、风险和决策日志。

```text
Use $prd-builder：根据以下会议纪要和三条用户反馈，为本季度现有客户试用写条件 PRD。请区分事实、证据、假设和待确认项；不要把所有提议放进 MVP；为核心流程给出状态、埋点和 Given/When/Then 验收。
```

## 输入不足时会发生什么

- 只有一句话想法时，得到的是问题假设卡和最小验证范围，不会得到虚构事实的完整 PRD。
- 只有会议纪要时，得到来源账本、冲突和待确认项；发言不会自动升级为需求。
- 要求无边界 MVP 时，得到候选池和带理由的范围切分，且要求具名决策人确认取舍。
- 没有基线或指标时，得到测量规格和补数动作，不会编造目标数值。

## 如何阅读输出

- `[事实]`、`[证据]`、`[假设]`、`[推断]` 与 `[待确认]` 表示不同可信度和处理方式。
- MVP 是本轮验证核心用户结果所必需的内容；后续候选不是承诺，非目标说明当前不做和重审条件。
- 每条核心需求应能定位到验收 ID、状态和埋点；无法验收的描述需要回到需求表重写。
- 开放问题、依赖、风险和决策日志中没有 owner 或时间的项，仍是交付阻塞。

## 如何与其他 Skill 串联

先用 `feature-discovery-interviewer`、`user-feedback-synthesizer`、`competitive-research-brief` 或 `metric-diagnosis` 补齐问题与证据。PRD 范围稳定后，可交给 `roadmap-prioritizer` 取舍、`prototype-brief-builder` 定义体验，或 `spec-to-implementation-plan` 拆成工程任务；需验证方案时使用 `experiment-designer`。

## 精简实际场景

团队提出“为现有客户做 AI 跟进建议”。先将销售会议中的“客户常忘记跟进”标为 `[推断]`，把“本季度现有客户试用”登记为已决范围。首版只保留一种受控导入、人工确认和保存事件；CRM API、报表和新客户自助开通移入后续候选或非目标。随后为上传、确认和保存分别写错误、权限、成功状态与验收，再让数据负责人确认事件口径。这样交付的是可审查的条件 PRD，而不是一份把愿望伪装成承诺的长文。
