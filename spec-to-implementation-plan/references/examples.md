# 规格转实施计划示例

以下是文档级示例，不代表对某个外部仓库执行过命令。三例均按 13 项压缩展示，重点是证据边界和可审查任务。

## 场景一：完整 PRD 加已读仓库证据

**输入摘要：** PRD 要求管理员导出本周订单 CSV；验收含权限拒绝、空结果和下载审计，数据 owner 已确认审计保留期。已读材料明确提供 `apps/admin/orders/export.ts`、`packages/order-query/src/week.ts`、`packages/audit-publisher/src/export.ts`、`apps/admin/orders/export.test.ts` 与 `docs/api/audit-events.md` 的职责和现有测试命令。

1. **计划卡与门槛：** 目标、验收、技术落点、数据/权限和发布/运行均通过；审计保留期由数据 owner 的输入确认。
2. **账本：** `[已知] AC-EXPORT-01` 为管理员只可导出本周；`[已知]` 审计保留期已满足上线配置。
3. **文件职责：** 五个已提供路径各自负责路由、查询、审计发布器、路由测试、事件 schema；证据是输入材料，不假设其他文件。
4. **关键路径：** 管理员请求 -> 权限校验 -> 周订单查询 -> CSV 流 -> 下载与审计；无订单返回空 CSV 和提示。
5. **接口：**
   - `I-01 OrderWeekQuery` 是请求/结果契约，定义 owner 为 `T-01`；查询模块为 runtime producer、导出路由为 consumer，consumes `weekStart` 和管理员身份，produces 订单行或空集合，拒绝时 `403`。
   - `I-02 AuditEvent` 是数据 schema，定义 owner 为 `T-02`；导出路由在运行时构造 event，审计发布器为 sink；schema 定义事件名、actor、周范围、结果计数、时间和幂等键。
   - `I-03 AuditPublisher.publish(event)` 是 capability，定义/提供 owner 为 `T-03`；审计发布器为 provider、导出路由为 consumer，consumes `I-02 AuditEvent`，produces 已确认写入或可处理失败。
   三者分别测试请求结果、schema 和调用结果。
6. **任务：** `T-01` 在查询职责中加入周范围/顺序单元测试并 produces `I-01` 查询行为；`T-02` 只在 `docs/api/audit-events.md` 定义 `I-02 AuditEvent` schema/fixture 并 produces 契约；`T-03` 只在审计发布器职责中 consumes `I-02` 并实现/produces `I-03 AuditPublisher.publish(event)` capability、确认/失败处理和契约测试；`T-04` 只在路由职责中 consumes `I-01`、`I-02` 和 `I-03`，实现 CSV/权限，在运行时构造 `I-02` 并调用 `I-03`；`T-05` 只在路由测试职责中加入端到端集成覆盖，不回改前四项职责。
7. **依赖与合并顺序：** `T-01 -> T-04 -> T-05`（请求/结果被路由消费）；`T-02 -> T-03 -> T-04 -> T-05`（schema 先被 capability 实现消费，路由最后消费 capability 并在运行时构造 event）。`T-01` 与 `T-02` 可并行；合并顺序为 `T-01`/`T-02`、`T-03`、`T-04`、`T-05`。每项验收后冻结职责；契约修订必须新建任务，不回头修改前项。
8. **测试：** 单元覆盖周边界，`I-02` schema 契约覆盖字段/幂等/失败，`I-03` capability 集成覆盖确认与失败，路由集成覆盖 `403`、空结果、CSV、runtime `I-02` 构造和 `I-03` 调用，人工检查下载文件名。
9. **数据/迁移：** 无存储 schema 变更；审计保留期已有 owner 确认，不默认无影响。
10. **发布：** 不使用 flag，理由是仅管理员入口且可用部署回滚；监控下载失败率和审计事件缺失，owner 为平台值班。
11. **验证：** `[未运行]` 在仓库根目录运行输入材料提供的测试命令；前提为测试数据库，期望三类断言通过。
12. **风险：** 审计发布失败可能造成审计缺失；平台值班依据失败率和事件缺失监控暂停发布并按既定回滚动作恢复。
13. **交接与最终判定：** 当前**通过**；从可并行的 `T-01`/`T-02` 开始，完成条件为五项任务验收、测试、审计确认和发布监控均有记录。

## 场景二：模糊需求“让通知更智能”

**输入摘要：** 没有用户、渠道、触发条件、成功指标、验收、仓库路径或数据权限信息。

1. **计划卡与门槛：** 目标、验收、技术落点、数据/权限、发布均为阻塞；范围仅限需求澄清，不承诺实现。
2. **账本：** `[未知]` “智能”的可观察行为、用户分群、通知渠道、频率、同意状态和效果指标。
3. **文件职责：** `[未知，待仓库证据]`；候选职责为通知触发、偏好/同意、模板和事件，不列文件名。
4. **关键路径：** 仅有待确认草图：事件 -> 资格/偏好 -> 候选内容 -> 渠道发送 -> 退订/失败处理。
5. **接口：** 无可承诺 `I-*`；待确认是否存在事件、偏好和发送提供者契约。
6. **任务：** `T-01` 产品/数据澄清用户、目标与验收；`T-02` 只读探索现有通知入口、同意状态、测试和命令；`T-03` 在前两项完成后起草接口与实现计划。
7. **依赖：** `T-01 -> T-03`，`T-02 -> T-03`；`T-01` 与 `T-02` 可并行。
8. **测试：** 仅定义未来验收需覆盖资格、频率、退订、发送失败和指标；层级待仓库证据确定。
9. **数据/迁移：** 同意状态和事件数据未知，禁止规划 schema。
10. **发布：** 若形成用户可见发送行为，未来需决定 flag、频率护栏、退订监控；目前不作结论。
11. **验证：** `[未运行]` 无仓库命令；阻断原因为未提供仓库路径和允许执行范围。
12. **风险：** 未经同意发送、频率伤害和不可衡量效果；owner 为产品/隐私/工程负责人。
13. **交接与最终判定：** 当前**不通过**；先完成三项探索，满足门槛后再写文件级任务。

## 场景三：未读代码库却要求“给出精确修改文件”

**输入摘要：** 用户说“给订单取消加原因字段，直接列具体文件”，但没有仓库、分支、路径、schema、API 或测试资料。

1. **计划卡与门槛：** 目标为条件通过；技术落点、数据、权限、发布阻塞。明确不输出精确文件。
2. **账本：** `[未知]` 原因是自由文本还是枚举、谁可填写、是否公开、保留期和现有取消契约。
3. **文件职责：** `[未知，待仓库证据]`；搜索线索为 `cancel`、`order`、`reason`、迁移目录和相邻取消测试。
4. **关键路径：** 候选流程为取消请求 -> 原因校验 -> 持久化 -> 响应/事件；每个跳点待读证。
5. **接口：** 候选 `I-01 CancelOrder` 的 consumes/produces、错误和兼容性均待现有 schema 确认，不造字段名或路由。
6. **任务：** `T-01` 运行最小只读搜索并阅读命中入口、schema、调用者和最近测试；`T-02` 依据证据编写契约/迁移计划；`T-03` 再拆实现与验证任务。
7. **依赖：** `T-01 -> T-02 -> T-03`，不可并行，因为后两项消费证据。
8. **测试：** `T-01` 找到现有测试层级；迁移、集成、权限和兼容测试待 evidence 后选择。
9. **数据/迁移：** 只有确认取消记录的存储和读写消费者后，才能决定回填、默认值、双读写或不迁移。
10. **发布：** 待确认旧客户端和下游事件消费者；若兼容风险存在，规划 flag 或版本化，不能默认可回滚。
11. **验证：** `[未运行]` 建议从仓库根目录只读搜索和现有相关测试开始；当前阻断为没有仓库访问证据。
12. **风险：** 虚构路径会把实施者带错；数据字段可能影响合规和消费者，owner 为服务/数据 owner。
13. **交接与最终判定：** 当前**不通过**；交付搜索词、阅读停止条件和三个顺序任务，精确文件只在 `T-01` 产生可定位证据后补入。
