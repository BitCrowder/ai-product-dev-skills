# 规格转实施计划使用说明

## 这个 Skill 解决什么问题

它把产品与技术输入变成可审查的工程计划，但先判断计划是否真的可实施。与“列任务”不同，它要求文件职责有证据、接口有消费者和产出、任务有可验证边界，并把数据、发布和恢复留在同一份交付中。

## 适合谁使用

产品经理、技术负责人、工程师、测试负责人和跨团队交付 owner 可在开始编码、拆 Issue、估算、评审或交接前使用。已有 PRD 或设计但不确定文件、接口、依赖和发布条件时尤其适合；陌生仓库应先用 `codebase-onboarding` 取得证据。

## 为什么普通提示词容易失败

“把这个 PRD 拆成任务”通常会跳过可实施性门槛，按惯例猜文件路径和接口，并把迁移、兼容、回滚、监控与验证留给最后。它也容易把一个跨层大任务写成无法独立审查的清单。该 Skill 要求每个结论回链证据、每个接口写 producer/consumer 与 consumes/produces、每个任务只消费前置已验收产出；缺证据时只交付探索计划。

## 使用前准备

尽量提供以下输入；不知道就标 `[未知]`：

```text
要支持的决定、目标用户、结果、范围、非目标和截止时间：
可观察验收：主路径、错误/恢复、权限、性能或数据正确性：
PRD、设计、技术规格、Issue 与已有决定的来源：
已读仓库路径/符号/接口 schema/测试与构建证据：
数据、权限、兼容、发布窗口、flag、监控和依赖团队约束：
```

没有已读仓库证据时，明确说“只做条件计划，不要猜文件路径”。需要找入口、测试或命令时，先使用 `codebase-onboarding`，再将它的证据账本交给本 Skill。

## 推荐调用方式

先说明希望计划支持什么决定，再附材料，并要求保留证据边界：

```text
Use $spec-to-implementation-plan：根据以下 PRD 和已读仓库证据，生成 13 项实施计划。只把有证据的路径列为文件；每个接口写 producer、consumer、consumes、produces、失败和兼容；每个任务必须独立可审查并有测试、迁移/发布/回滚/监控与验证命令。
```

## 如何处理三种输入质量

- **完整 PRD 加仓库证据：** 通过门槛后产出文件职责、`I-*` 接口、`T-*` 任务、依赖图和分层测试。PRD 完整不等于仓库路径已知。
- **模糊需求：** 产出条件计划和最小探索/澄清任务。没有验收、用户、权限或数据边界时，不承诺实现任务或上线。
- **未读仓库却要精确文件：** 只输出候选职责和搜索词，例如业务术语、事件名或相邻测试；路径一律写 `[未知，待仓库证据]`。

## 如何阅读输出

- 13 项中的“通过/条件通过/阻塞”决定能否开始实施；最终判定为“通过/有条件通过/不通过”。有条件通过只允许不影响首个任务范围、接口、数据、权限、发布或验收的具名条件；其余阻塞均为不通过。
- `[已知]` 可追溯，`[推测]` 必有验证动作，`[未知]` 会显示它阻断的决定。
- `I-*` 说明任务间或系统边界的输入输出；`T-*` 是可单独审查的交付物。`T-A -> T-B` 表示 B 消费 A 的结果。
- 验证命令中的 `[未运行]` 只是计划。只有真实执行记录可称为通过或失败。

## 与其他 Skill 的衔接

先用 `prd-builder` 稳定目标、范围和验收，用 `prototype-brief-builder` 明确体验状态；仓库陌生或命令未知时用 `codebase-onboarding`。本 Skill 的交付再交给 `issue-to-pr` 执行、`test-generator` 细化测试，或 `launch-readiness-checklist` 审核上线条件。

## 最小完整例子

"管理员导出周订单"已有权限、空结果、审计验收和已确认的审计保留期，且已读路由、查询、审计发布器、测试和审计 schema。计划会先由 `T-02` 定义 `I-02 AuditEvent` schema，再由 `T-03` 实现/produces `I-03 AuditPublisher.publish(event)` capability；路由 `T-04` consumes 请求/结果、schema 与 capability，在运行时构造 event 并调用 publisher。三种责任不能合并为一个接口 ID，任务按单向依赖合并。相反，只有“让通知更智能”时，输出只会是澄清与只读探索任务，不会伪造文件、接口或数据 schema；完整三例见 `examples.md`。
