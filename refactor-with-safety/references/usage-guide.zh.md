# 安全重构助手使用说明

## 这个 Skill 解决什么问题

它把结构改善变成可回退、可审查的工程工作：先明确哪些行为和公共契约不能变，补最小特征化测试与性能基线，识别依赖缝隙，按小步验证，再在证据不足时停下来。

## 为什么普通提示词容易失败

“把这个文件拆干净”常把当前实现当成唯一上下文。普通提示容易只关注内部代码形状，遗漏调用方、存量数据、事件、默认值、权限、副作用顺序和旧客户端；也会把新功能或 Bug 修正混入重构，导致绿灯不能说明哪一类行为仍被保护。

## 适合谁使用

- 需要拆大文件、抽取模块或去重，同时保留外部行为的工程师。
- 负责公共 API、事件、配置、数据模型或 SDK 迁移的维护者。
- 希望让重构提交可独立审查、可回滚并保留性能/兼容证据的技术负责人。

## 使用前准备什么

提供重构目标和非目标、代码入口与调用方、现有测试和允许命令、公共 API/数据/事件/副作用、兼容窗口、性能敏感路径、工作区基线与回滚限制。未知内容可以明确说明，Skill 会生成 `GAP-*` 和停止条件，不会编造消费者或结果。

## 推荐调用方式

```text
Use $refactor-with-safety：目标是拆分 billing/settlement.ts，非目标是不改变金额、错误、重试和消息语义。
已知入口、消费者、测试、事件与性能资料是……；未知项是……；允许命令是……。
请先建立 B-* 行为基线、C-* 公共契约和 P-* 性能基线，分离机械/语义/功能变更，再给出可回滚的 S-* 与实际 E-* 证据格式。
```

## 输入不足时会发生什么

没有行为、非目标、消费者、测试或性能条件时，输出会限制为澄清问题、搜索线索、最小特征化测试建议、`GAP-*` 与停止条件。它不会删除旧 API、迁移数据、扩大到全仓整理，或把未运行测试写为安全结论。

## 如何阅读输出

先检查 `B-*` 是否是调用方真正可观察的结果，再看 `C-*` 是否覆盖 API、数据和副作用。接着看依赖边界与 `P-*` 是否使抽取和性能判断可解释；最后逐项核对 `S-*` 的分类、验证和回滚点。只有真实 `E-*` 证明的项目可称已验证，`GAP-*` 表示仍需补的边界。

## 如何与其他 Skill 串联

入口和测试拓扑不清时先用 `codebase-onboarding`；复杂故障先用 `bug-debugging-playbook`；需要补风险驱动测试时交给 `test-generator`；功能/Issue 的最小实现用 `issue-to-pr`；重构 diff 完成后用 `code-review-assistant` 审核契约与回归，发布前再接 `launch-readiness-checklist`。

## 精简实际场景

面对“给公共 SDK 改名并删除旧导出”，先列 `C-*` 的 Web、CLI、插件和版本窗口，再以适配导出迁移已知消费者。旧导出只能在实际消费者、兼容期和契约/性能结果齐全后删除；否则交付的是可继续执行的 `GAP-*`，而不是一份看似干净但会破坏插件的 diff。
