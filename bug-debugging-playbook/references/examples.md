# 调试场景示例

以下是文档级输入和合格输出骨架，不代表执行过所述业务仓库或命令。

## 场景一：稳定复现的接口错误

**调用：**

```text
Use $bug-debugging-playbook：POST /v1/invoices 在 staging 对已取消合同返回 500，
本地同一请求返回 422。日志有 request_id、时间和数据库错误。请定位后修复。
```

**合格输出骨架：**

- `[事实]`：E-01 记录 staging 的 `request_id`、时间、500 与数据库错误；E-02 记录本地同一最小请求的 422。两条证据的应用版本、schema 版本和脱敏状态均已记录。
- 最小复现：固定已取消合同 fixture、请求体和账户权限；失败信号是 staging 500，成功对照是有效合同返回预期响应；复现率和次数单列。
- 差异矩阵先比较 schema、应用版本、feature flag、权限和合同数据。`H-01` 不是“数据库坏了”，而是“取消状态在 staging 的映射漏掉 422 校验”。`X-01` 只切换同一 fixture 的状态，预测是仅取消状态进入未处理路径；反证是所有状态都出现同一数据库错误。
- 若 `X-01` 与最小调用链证明机制，才写 `[已确认根因]`；修复前建立取消状态的红灯断言，绿灯后验证有效合同不变、原始请求和 staging 门禁。若只有统一错误码的改动，则标记 `[缓解措施]`。

## 场景二：偶发前端卡死

**调用：**

```text
Use $bug-debugging-playbook：少量用户切换工作区后页面偶发卡死，刷新恢复；
没有稳定步骤，只有 Sentry 堆栈、浏览器版本和部分会话时间。请修复。
```

**合格输出骨架：**

- `[事实]`：E-01 只有 Sentry 堆栈、浏览器版本和会话时间；工作区 ID、路由、feature flag、网络、状态转换和 CPU/长任务数据为 `[未知]`。不能称为最小复现。
- 结论是“不可复现，停止猜测性修复”。观测增强在工作区切换开始/完成、请求生命周期、错误边界和超过阈值的主线程任务写入脱敏 session/trace ID、版本、flag、耗时和状态；采样窗口、保留期、Owner 与隐私边界明确。
- 环境矩阵比较卡死/正常会话的浏览器、版本、工作区规模、flag 和网络。`H-01` 仅为“状态转换可能等待未完成请求”；`X-01` 固定会话与数据，在测试环境只控制网络延迟。未采集到关联证据前，任何 timeout 或刷新逻辑只能作为可回退 `[缓解措施]`，不能宣称根因修复。

## 场景三：用户要求先改最可能的代码

**调用：**

```text
Use $bug-debugging-playbook：支付回调偶尔重复扣款，最可能是 retry.ts；
先把 retry 次数改成 1，之后再看日志。
```

**合格输出骨架：**

- 将 `retry.ts` 列为 `[假设]`，而非事实；必须先收集支付 provider 事件 ID、幂等键、回调时间线、重试配置、重复扣款样本和未重复成功对照。
- 最小复现用固定回调事件和幂等键模拟“响应丢失后重试”；`X-01` 只改变重试触发，预测是相同事件发生多次业务扣款。`X-02` 可在其后单独验证幂等键持久化，不能与降低重试次数同时执行。
- 若降低次数只减少影响，写为 `[缓解措施]`，包含漏处理风险、回滚和撤除条件。只有机制证据证明扣款路径未在同一事件上幂等，才写 `[已确认根因]`，并以“同一事件至多一次扣款”和“独立事件仍可处理”为回归门禁。

## 易误用反例

```text
“日志说 timeout，所以同时把超时翻倍、重试减半、缓存关闭，再看哪个用户不投诉。”
```

这同时改变多个变量，结果无法确认因果。应拆为带预测和反证信号的 `X-*`，或在不可复现时先补观测。
