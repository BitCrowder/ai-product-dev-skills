# Bug 调试证据链手册：中文使用说明

## 解决什么问题

这个 Skill 用于把“坏了”“偶发卡死”“可能是某文件”的描述，转成可审查的调试交付：症状与影响、证据时间线、最小复现或观测增强、可证伪假设、单变量实验、根因/缓解结论、最小修复和回归门禁。

普通提示词容易直接猜一个修复点，跳过环境、数据、时间和成功对照；结果可能暂时压低报错，却不知道故障机制是否仍在。此 Skill 要求每个结论回链到证据，并让“不能复现”成为补观测的明确分支。

## 适合谁使用

- 需要调查接口异常、崩溃、卡死、重复副作用、回归或 flaky test 的工程师和 on-call。
- 需要判断是永久修复、临时缓解还是继续采集证据的技术负责人。
- 需要把调试结论交接给实施、测试、发布或事故沟通负责人的协作团队。

## 使用前准备

提供症状、期望/实际、影响范围、时间和时区、最少一条日志/trace/截图或命令结果、成功对照、环境/版本、近期变更和可访问代码/测试。敏感日志先脱敏；未知信息可以不补，但要如实说明缺失。

## 推荐调用方式

```text
Use $bug-debugging-playbook：
症状：...
期望/实际：...
影响和首次时间（含时区）：...
复现步骤、最小数据和成功对照：...
日志/trace/指标及关联 ID：...
环境、版本、flag、权限和近期变更：...
约束：允许的环境、数据边界、变更/回滚窗口：...
```

要求回答按模板输出，并说明哪些是 `[事实]`、`[推断]`、`[假设]` 与 `[未知]`。若用户指定“直接改某文件”，它仍先把该点降为待验证假设。

## 输入不足时会发生什么

缺少期望、影响或证据时，输出澄清问题和停止条件；不能稳定复现时，输出观测增强方案、采样与隐私边界、Owner 和触发条件。此阶段可以提出可回退的缓解措施，但不能虚构根因、红绿测试或永久修复结果。

## 如何阅读输出

先看调试卡确定影响与边界，再按 `E-*` 验证时间线。`H-*` 是可被推翻的机制候选，`X-*` 每次只改变一个变量。只有机制解释复现、环境差异并有独立验证时，结论才是 `[已确认根因]`；任何仅降低影响的做法都应是 `[缓解措施]`。最后检查回归门禁是否覆盖原始症状和未受影响对照。

## 如何串联其他 Skill

- 不知道入口、配置、测试命令或数据流时：`codebase-onboarding` -> 本 Skill。
- 需要把已确认的修复推进为范围受控的改动和 PR：本 Skill -> `issue-to-pr` -> `code-review-assistant`。
- 根因明确但覆盖不足时：本 Skill -> `test-generator`。
- 需要对外说明影响、缓解与下一步：本 Skill -> `stakeholder-update-writer`。

## 精简实际场景

“staging 的取消合同请求返回 500，本地返回 422”不应直接得到“修 catch”。先以 request ID 和时间建立 `E-*`，用相同 fixture 比较 schema、版本、flag 与权限，选择一个差异运行 `X-*`。如果取消状态确实绕过校验并导致数据库写入，再把该机制标为根因，补取消状态红灯、最小修复、有效合同对照和 staging 验证；若只统一错误码，则它只是缓解。
