# 用户反馈综合使用说明

## 何时调用

在已有用户反馈、需要识别已覆盖人群中的问题模式、保留证据并决定下一步研究或缓解动作时调用。先说明要支持什么决定，不要只说“把反馈排个优先级”。

## 最小输入包

未知项可留空，但必须标为 `[未知]`：

```text
要支持的决定与截止时间：
产品区域、版本和目标工作流：
原始反馈或可定位摘录：
反馈单位、时间窗、纳入/排除规则：
渠道、记录标识、匿名作者/账户、关联工单/会话：
目标分群、可用分群字段和未覆盖分群：
已知重复、批量事故、转发、机器人/内部记录：
隐私、保留和访问限制：
结论将影响的下一步决定：
```

## 推荐执行顺序

1. 先写综合卡，固定反馈单位和分母；分别数原始记录、去重事件和独立用户。
2. 为每条材料建立来源编号与安全摘录，再按稳定标识、关联关系、同一事件和时间窗去重；保留合并理由。
3. 先建编码本，分开记录问题、期望结果、情境、当前做法、影响、方案请求和反例；试编码后再修改代码版本。
4. 按分群、版本、渠道和情境聚类，保留冲突与无法归类项。频率和严重性分别报告，不生成自动优先级。
5. 将主题改写成有范围的洞察和可被削弱的问题假设，列替代解释、验证动作和停止条件；未补齐决策输入前不承诺路线图。

## 何时暂停并追问

出现下列任一情况时，不直接生成主题排名或产品建议：

- 没有原始材料、来源编号、时间窗或反馈单位。
- 不知道 100 条记录中是否有同一用户追问、关联工单、批量事故或转发。
- 只有五条无渠道、无作者/账户、无分群的零散评论，却要求代表性结论。
- 要求把最高频方案请求直接排进路线图，未提供影响、战略、成本、可行性、风险、依赖或验证结果。
- 矛盾反馈未按分群、版本、渠道、时间和情境拆开，或证据涉及敏感资料且没有处理边界。

## 交付解读

- `[用户表达]` 是原话和主观看法；`[可观察行为/事实]` 是可定位的事件、动作或记录。
- `[研究者编码]` 说明如何分类；`[研究者推断]` 只能基于已列证据且必须注明适用范围；`[未知]` 不能用低置信度掩盖。
- `频率` 是指定分母内的出现情况；`严重性` 是影响证据；两者不自动决定优先级。
- `待验证候选机会` 是下一步研究或排序的输入，不是已批准功能。

完整字段见 `templates.md`，交付前使用 `checklists.md`，三种压力场景见 `examples.md`。
