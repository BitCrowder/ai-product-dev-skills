# 风险驱动测试生成器使用说明

## 这个 Skill 解决什么问题

它把“补测试”转成可审查的测试决策：应保护什么行为、风险在哪里、为什么选这个测试层级、哪些 fixture 和 mock 可以信任、Bug 是否真的能在修复前失败，以及实际运行结果还留下什么缺口。

## 为什么普通提示词容易失败

普通提示往往只生成一串 happy path、框架语法或覆盖率目标。它容易跳过调用方真正观察的错误状态、权限、并发和协议，也会在修复后补一个直接通过的 Bug 测试。大量快照和 mock 调用断言看似覆盖广，却可能在实现重构时频繁破碎，或根本抓不住真实故障。

## 适合谁使用

- 需要给功能、接口或用户流程补测试的工程师。
- 修复 Bug 后需要留下可验证回归门禁的维护者。
- 在重构、发布或代码审查前需要判断测试缺口的负责人。
- 想将验收、风险和测试命令交接给下一位执行者的技术负责人。

## 使用前准备什么

准备行为与验收、相关代码和调用方、风险/事故信息、现有测试与 CI 约定、可运行环境和数据限制。Bug 场景还应提供修复前版本或能定位的原始失败信号。未知项可以直接说明；Skill 会将它们列为阻断或缺口，而不是猜测。

## 推荐调用方式

```text
Use $test-generator：
行为：管理员撤销邀请后，旧 token 必须不能接受；有效 token 仍能接受。
风险：越权加入组织，生产已出现同一 token 撤销后返回 201。
代码与约定：auth/invitations.ts；请先阅读相邻测试和 package scripts，不要猜框架命令。
限制：可访问修复前 commit 和临时数据库；token 必须脱敏。
请给出风险矩阵、最低有效测试层级、fixture/mock 边界、修复前红灯、修复后命令证据和剩余缺口。
```

## 输入不足时会发生什么

缺验收时只会得到澄清问题和停止条件；缺测试约定时先查相邻测试；无法回到修复前版本时会产生 `ALT-*` 替代证据与恢复红灯的条件。它不会把未运行的命令、生产日志或覆盖率数字写成自动化回归已证明。

## 如何阅读输出

先看 `B-*` 是否说清调用方可观察的结果，再看 `R-*` 是否覆盖最坏失效与层级理由。接着审查 fixture/mock 表是否保留了被测责任，最后核对 `RED-*`、`GREEN-*` 和 `T-*` 的目录、命令、退出码与限制。通过结论必须能回链这些证据；`GAP-*` 指出仍需谁在何种条件下补齐什么。

## 如何与其他 Skill 串联

先由 `codebase-onboarding` 找到入口、测试拓扑与本地约定；`spec-to-implementation-plan` 或 `issue-to-pr` 提供验收与范围；复杂或间歇 Bug 先经过 `bug-debugging-playbook` 的复现和根因证据。生成的矩阵、红绿账本和缺口可交给 `code-review-assistant` 审查，再供 `refactor-with-safety` 或 `launch-readiness-checklist` 使用。

## 精简实际场景

团队要为“重复支付回调不得重复入账”补测试。此 Skill 会要求提供事件 ID、幂等键、入账状态和队列/数据库边界，将规则放在单元、真实持久化和并发放在集成、provider payload 放在契约；它会拒绝只断言 handler 被调用两次，并在无法重放旧故障时明确记录 `ALT-*` 和自动化缺口。
