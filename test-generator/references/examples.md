# 风险驱动测试示例

以下是文档级示例，不声称已在某个业务仓库执行。所有路径、命令和结果在实际任务中必须替换为真实证据，不能照抄为通过结论。

## 场景一：为新 API 补测试

**原始请求：** `为 POST /v1/invoices 补测试：有效订单创建发票；没有库存时返回错误。代码在 services/invoice.ts，现有项目用 Vitest。`

**V1 的不足：** V1 会列出单元、集成、边界和命令，却没有区分库存扣减、持久化、事件发布和 HTTP 错误映射属于哪些风险边界，容易只写 service mock 测试。

**V2 的输出骨架：**

```markdown
# 测试卡：创建发票 API
- [事实]：请求给出两个行为和 `services/invoice.ts`；尚未提供路由、schema、事务边界和相邻测试路径。
- [未知]：权限、幂等键、库存并发语义和事件契约；阻断最终层级、fixture 与命令结论。
- 停止条件：未读到现有 Vitest 配置与相邻测试前，不编造测试文件或脚本。

| ID | 调用方/用户 | 前置状态与输入 | 动作 | 期望可观察结果 | 成功对照 |
|---|---|---|---|---|---|
| B-01 | 有权限的商户 | 可售订单 | `POST /v1/invoices` | 发票持久化，库存按一次扣减，返回公开 ID | 相同订单再次查询仍一致 |
| B-02 | 有权限的商户 | 无库存订单 | 同一请求 | 明确业务错误，无发票/库存副作用 | B-01 仍可成功 |

| R-ID | 对应 B-ID | 首选层级 | 理由 | 稳定断言 |
|---|---|---|---|---|
| R-01 | B-01 | 单元 + 集成 | 单元验证计价/状态规则；库存与发票事务不能由 mock 证明 | 业务总额；临时数据库中的发票和库存变化 |
| R-02 | B-02 | 集成 + 契约 | 需要验证回滚和公开错误 payload | 无持久化副作用；错误码和 schema |
| R-03 | B-01 | 集成 | 并发请求可能重复扣减 | 相同幂等键只产生一次副作用 |

fixture：使用临时数据库中的一个订单、一种库存状态和固定时钟；每例事务回滚。支付/邮件客户端是边界 mock，但请求 payload 与错误映射由 fake server 契约验证。
```

**复测结论：** V2 不会把“Vitest”直接推断成测试命令，不以 controller mock 调用次数覆盖事务风险，并显式保留权限、并发和事件契约的未知项。

## 场景二：为已修复 Bug 加回归测试

**原始请求：** `已修复：管理员撤销邀请后，旧邀请链接仍可接受。请补回归测试。修复在 auth/invitations.ts；生产日志显示同一 token 撤销后仍返回 201。`

**V1 的不足：** V1 只说“当可行时先写失败回归测试”，没有要求修复前版本、实际失败信号、`GREEN` 回链或无法回退时的替代证据，修复后绿色测试可能无法捕获原 Bug。

**V2 的输出骨架：**

```markdown
| B-ID | 前置与动作 | 期望结果 | 成功对照 |
|---|---|---|---|
| B-01 | 管理员撤销 token 后以同一 token 接受邀请 | 拒绝且不创建成员 | 未撤销的有效 token 可创建一名成员 |

| R-ID | 层级 | 关键断言 | 边界 |
|---|---|---|---|
| R-01 | 集成 | 撤销状态持久化后接受端返回公开拒绝且成员数不变 | 管理员权限、过期 token、并发接受 |
| R-02 | 契约 | 接受端拒绝响应的错误码与 payload 稳定 | 旧客户端兼容 |

| E-ID | 阶段 | 完整命令或动作 | 结果 |
|---|---|---|---|
| RED-01 | 修复前失败 | 在修复前 commit 的隔离数据库运行“撤销后接受”测试 | 必须因收到 201 或创建成员失败；fixture 启动错误不计入 |
| GREEN-01 | 修复后通过 | 在修复后 commit 运行同一测试和“有效 token”对照 | GREEN-01 必须回链 RED-01；撤销 token 被拒绝、有效 token 成功 |
| T-01 | 邻近验证 | 运行邀请模块与契约套件 | 记录实际命令、退出码和摘要 |
```

**无法获得修复前版本时：** 使用 `ALT-01` 引用带时间、token 脱敏方式和响应状态的原始生产日志，记录“历史工件不能证明新测试会红”；恢复 `RED-01` 的条件是取得修复前 artifact 或在受控副本撤销修复。结论最多是**有条件通过**。

**复测结论：** V2 要求 Bug 回归先证明可捕获原始症状；无法做到时不伪造红灯，而是把限制、替代证据和恢复条件写入交付。

## 场景三：只追求覆盖率百分比

**原始请求：** `本周把 payment 模块覆盖率从 76% 提到 90%，先补快照和 mock 调用次数，测试全绿就可以合并。`

**V1 的不足：** V1 虽强调行为和风险，但没有把“覆盖率不是质量代理”变成停止规则、测试层级判断或拒绝浅层断言的交付结构。

**V2 的输出骨架：**

```markdown
- 结论：不能把 90% 作为通过条件；请提供支付行为、失败成本、实际未执行路径、权限/幂等/退款契约与现有套件证据。
- [推断]：支付模块的高风险通常不是未执行分支数，而是重复扣款、金额/币种精度、拒绝/超时映射、权限隔离和 webhook 契约；先以代码与事故记录验证。

| R-ID | 行为 | 首选层级 | 可维护断言 | 拒绝的替代 |
|---|---|---|---|---|
| R-01 | 相同幂等键只扣款一次 | 集成 | ledger 仅一笔、公开响应可重放 | mock 调用次数 |
| R-02 | provider 超时不标记已支付 | 集成 + 契约 | 状态为待处理、错误可重试 | 整页快照 |
| R-03 | 非财务角色不能退款 | 集成 | 403、账本不变、审计事件 | 私有 helper 断言 |

结论：只有当 R-01 至 R-03 的命令证据存在且缺口被接受时才可通过；覆盖率报告可附在 T-02，但不能替代这些断言。
```

**复测结论：** V2 明确拒绝以快照、浅层 render、mock 调用次数或覆盖率百分比制造虚假质量，并把风险矩阵和实际命令证据作为合并判断依据。
