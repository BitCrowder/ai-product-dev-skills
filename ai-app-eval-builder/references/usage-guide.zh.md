# AI 应用评测设计器使用说明

## 这个 Skill 解决什么问题

它将“模型看起来好不好”变成可复跑的发布证据：评什么能力和风险、测试数据从哪里来、不同 grader 如何互相校验、哪些切片不能退化、以及线上真实失败如何安全地回流到下一版离线数据集。

## 为什么普通提示词容易失败

普通提示经常直接要“准确率”或一组好问题，遗漏用户分布、泄漏和近重复，也让同一个 LLM 既生成又打分。平均分上升时，账户越权、错误退款、伪引用、长上下文或小语种失败仍可能变差。它还容易只看最终答案，忽略 RAG 是否找到了证据、Agent 是否选择了合法工具和参数。

## 适合谁使用

- 负责 LLM、RAG、Agent、聊天助手或 AI 工作流质量的产品、工程和研究人员。
- 要比较模型、提示词、检索/index、工具 schema、权限或编排策略的发布负责人。
- 需要将生产投诉、人工升级和 trace 转为隐私受控回归集的运营与质量团队。

## 使用前准备什么

准备用户任务与非目标、失败成本、baseline/candidate 的完整版本、现有黄金题、可脱敏的生产失败候选、模型/检索/工具架构、成本延迟预算、人工 reviewer 和线上监控限制。未知项可以直接写出；Skill 会给出 `GAP-*` 与停止条件，而不会编造分数。

## 推荐调用方式

```text
Use $ai-app-eval-builder：
决定：比较新的 RAG reranker 是否可以对 10% 客服流量灰度。
能力与风险：退款/取消政策必须有支持引用；伪引用和未授权账户信息是阻断。
版本：baseline/candidate 的模型、提示词、index 和 reranker 版本如下……
数据：80 条黄金 FAQ；有待审批的脱敏升级 trace；还没有小语种失败样本。
限制：p95 不超过 2.5 秒，单次成本不超过……；两名 reviewer 可每周校准一次。
请生成 C/R/D/G/E/Gate 台账、RAG 分层 grader、泄漏/去重检查、judge 校准和线上回流计划；不要把未知写成已验证。
```

## 输入不足时会发生什么

没有失败成本、生产分布或版本时，输出会停在澄清问题、候选切片和 `GAP-*`，而不是给出任意百分比。没有人工金标时，LLM judge 只能帮助发现问题，不能单独作为发布门禁。生产数据不能安全使用时，仍可建立经审核的黄金/合成集，但结论会明确不能代表线上。

## 如何阅读输出

先看 `C-*`/`R-*` 是否让发布决定有边界，再看 `D-*` 是否覆盖黄金、失败、困难、对抗及代表性限制。随后核对 `G-*`：确定性规则保护什么，rubric 是否可复现，人工和 LLM judge 是否被校准。最后审查 `E-*` 与 Gate：关键切片、成本、p95、稳定性是否独立通过，及上线后的回流、告警和回滚是谁负责。

## 如何与其他 Skill 串联

`prd-builder` 或 `experiment-designer` 提供目标、指标与实验边界；复杂线上故障先经 `bug-debugging-playbook` 留下可复核证据。`codebase-onboarding` 可帮助确认模型、索引、工具和日志版本。评测结论、缺口和发布门禁交给 `launch-readiness-checklist`，再由 `stakeholder-update-writer` 对外同步。

## 精简实际场景

运营 Agent 要从“生成退款草稿”扩展到“提交退款”。本 Skill 会把客服和管理员作为权限切片，独立判定工具 allowlist、参数、幂等键、循环和副作用，而不是只给最终回复打分；上线后将经审批的人工升级和异常 trace 去重、标注并冻结为下轮 dataset version。
