# Issue-To-PR 中文使用说明

## 解决什么问题

将任务单转成能被审查者验证的工程交付：先确认 Issue 是否可执行，再保护现有工作区，建立复现与失败测试，做最小改动，留下命令证据，并把风险与回滚写进 PR。

## 为什么普通提示词容易失败

“修复这个 Bug 并开 PR”常把未知环境、模糊验收、用户未提交改动和重构冲动藏起来。没有停止规则时，代理容易猜路径、编造测试结果，或在无法复现时交出看似合理的修复。本 Skill 要求把这些不确定性变成标签、阻塞和下一步。

## 适合谁使用

适合接手 Issue 的工程师、技术负责人、AI 编程协作者和需要审查证据的 reviewer。它适合已有最小仓库上下文的执行任务，不替代产品定义、代码库导览或深度根因排查。

## 使用前准备

- 提供 Issue 原文、验收、非目标、是否关闭 Issue 与发布约束。
- 为 Bug 提供复现步骤、环境、日志/截图、样本和最近变化；为功能提供主路径与异常状态。
- 提供仓库路径、目标分支、允许命令、当前工作区状态和已有用户改动归属。
- 提供相关路径/测试/CI 资料；没有时允许 Skill 只输出搜索线索与调查任务。

## 推荐调用方式

```text
Use $issue-to-pr：处理 Issue #42。目标是……；验收为……；非目标为……。
仓库在……，目标分支为……，当前已有改动为……；允许运行……。
Bug 复现步骤/环境/日志为……；若无法复现，请只交付阻塞与最小观测，不要声称修复。
```

## 输入不足时会发生什么

验收不清时，输出可执行性卡和澄清问题；仓库落点未知时，输出搜索词与阅读停止条件；测试无法运行时，如实标记未运行或失败；Bug 无法复现时，停止实现并交付调查、观测和重新进入条件。不会虚构文件、结果或 PR。

## 如何阅读输出

先看可执行性卡，确认是否可以编辑；再看工作区保护和复现/TDD 账本，检查红灯与绿灯是否真实；最后用验收矩阵核对每条 AC 是否有改动和证据。PR 的“未验证项”与“风险、回滚”是交付的一部分，不是附注。

## 如何与其他 Skill 串联

需求尚未可验收时先用 `prd-builder` 或 `spec-to-implementation-plan`；仓库入口不清时先用 `codebase-onboarding`；复杂或不可复现故障先用 `bug-debugging-playbook`；测试缺口较大时使用 `test-generator`；准备合并前让 `code-review-assistant` 审查 diff，发布风险较高时交给 `launch-readiness-checklist`。

## 完整精简场景

“空活动项目仪表盘崩溃”先把“空数组显示空状态、正常列表不变”写成 AC，并声明不改活动排序。确认分支和用户改动后，运行空活动测试取得红灯；只在已有渲染边界增加空状态映射，再取得绿灯与相邻测试证据。PR 关联 Issue，列出两项验收、命令结果、空状态与权限状态的风险，以及无数据副作用的回滚边界。若空活动场景不能复现，交付的应是环境差异和所需 fixture，而不是猜测性代码。
