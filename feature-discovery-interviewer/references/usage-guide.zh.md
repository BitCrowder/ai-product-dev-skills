# 功能探索访谈使用说明

## 何时调用

在决定是否解决一个问题、为谁解决以及下一步该做访谈、原型还是停止前调用。先说明要支持什么决定，不要只说“帮我验证这个功能”。

## 最小输入包

未知项可以留空，但要明确标成 `[未知]`：

```text
要支持的决策与截止时间：
目标用户、分群和相关工作流：
待验证的问题假设或功能想法：
已有证据、反例和不可触碰的假设：
招募渠道、纳入/排除条件、地区/语言、激励：
访谈方式、时长、是否录音、隐私限制：
```

## 推荐执行顺序

1. 先把功能名改写为问题假设：谁在何时为了完成什么任务遇到什么困难；写出支持预测、削弱预测和替代解释。
2. 用分群、渠道和排除条件设计招募；记录哪些人不会被覆盖，别把方便招到的人等同于目标用户。
3. 开场取得知情同意，说明目的、录音、匿名化、退出权和资料用途。
4. 用“最近一次”开启，再沿事件、过程、决定、替代方案、成本和反例追问。核心问题不展示或推销方案。
5. 每条笔记分开填写原话、实际行为、研究者推断和未知项；结束后先保存反例与矛盾，再跨访谈聚类。

## 何时暂停并追问

出现下列任一情况时，不直接生成结论：

- 没有要支持的决策、目标用户或工作流。
- 只有功能名称，无法说明其假设的问题、替代方案或反例。
- 招募渠道、排除条件或激励不明，却要求代表性结论。
- 要求“让用户承认”“证明值得做”或把未来意愿当作验证。
- 没有录音/数据用途同意，或请求敏感、机密、超出研究所需的信息。

## 交付解读

- `[用户表达]` 是受访者的原话或判断，不自动证明实际行为。
- `[实际行为]` 是有时间、情境和行动细节的经历；它仍只代表该受访者和场景。
- `[研究者推断]` 必须列出证据、分群、反例和替代解释。
- `[未知]` 表示没有合格材料或未覆盖的分群，不能用“低置信度”替代。

完整模板见 `templates.md`，交付前运行 `checklists.md`，三种典型边界见 `examples.md`。
