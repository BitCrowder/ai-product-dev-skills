# 证据驱动代码审查使用说明

## 这个 Skill 解决什么问题

它将代码审查从“读几行并给意见”变成可交接的风险判断：需求/契约对照、完整 diff 与相邻上下文、带证据的发现、测试缺口和明确合并结论。

## 为什么普通提示词容易失败

普通提示词常只总结改动、相信测试名称、把个人风格当 Bug，或在没有 PR 意图和调用方时杜撰影响。另一种失误是要求“只夸优点”后忽略真实风险。本 Skill 要求每项发现有触发条件与证据，证据不足时降为缺口。

## 适合谁使用

- 审查功能、Bug 修复、接口、迁移、权限和性能相关 PR 的工程师与维护者。
- 需要在合并或发布前留下审查风险、验证范围和 owner 的技术负责人。
- 希望复核测试是否真正保护公开行为的测试/质量负责人。

## 使用前准备什么

- PR 说明、base/head 完整 diff、需求/验收、非目标和发布约束。
- 改动行附近的定义、调用方、状态/数据流、错误路径、消费者和相邻测试。
- 已运行测试/CI/构建的完整命令、环境、退出码和关键输出；没有就明确未运行。
- 数据、权限、外部副作用、并发、兼容窗口、性能预算和可访问的平台信息。

## 推荐调用方式

```text
Use $code-review-assistant：审查 PR #184。base/head 是 <...>；需求/验收是 <...>；非目标是 <...>。
完整 diff 与这些上下文可访问：<路径/链接>。已运行验证为 <命令、环境、退出码>。
请按 F-* 输出：严重度、置信度、精确路径行号、触发条件、影响、证据和最小修复方向；同时给出需求/契约对照、GAP-*、测试缺口和合并结论。
```

## 输入不足时会发生什么

Skill 只对实际读取范围下结论。缺完整 diff、需求、消费者、测试或环境时，会列 `GAP-*`、最小澄清问题与建议验证；不会补造文件、行号、测试结果或把理论风险写成缺陷。

## 如何阅读输出

- `F-*` 是按 P0 到 P3 排序、可行动的发现；先看触发条件和影响，再看证据与最小修复方向。
- `RC-*` 将需求或公开契约与实际变更对应；`GAP-*` 说明无法判断的边界，不等于已经发现 Bug。
- “通过”仍受审查范围限制；“有条件通过”必须有可接受的缺口、owner 和恢复条件；P0/P1 通常导致“不通过”。

## 如何与其他 Skill 串联

- PR 落地前：`issue-to-pr` 提供验收、红绿测试和变更证据，再交给本 Skill 独立审查。
- 症状或根因不清：先用 `bug-debugging-playbook` 建立证据链，避免审查阶段猜测机制。
- 发现测试缺口：交给 `test-generator` 设计风险驱动验证；需安全重构时使用 `refactor-with-safety`。

## 精简实际场景

接口字段改名时，输入应同时给出兼容窗口、旧消费者和契约测试。若 diff 删除旧字段而消费者仍读取它，输出是带路径行号和旧客户端触发条件的 P1 发现；若只给序列化器文件却没有消费者或兼容需求，则只能记录 `GAP-*`，不能推断 API 已经破坏。
